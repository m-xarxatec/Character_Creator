# 7.4 — Publicar la versión en GitHub

> Último paso del MVP (Fase 7). Depende de 7.1, 7.2 y 7.3. Decisión D15 (solo si ya hay build de Windows).
> **Publicar no se puede deshacer del todo** (alguien puede haber descargado el archivo). El modelo **prepara**; el responsable **publica**.

## 1. Objetivo y «Hecho cuando»

**Objetivo:** una versión 0.1.0 descargable desde GitHub, con sus notas y su suma de control.

**Hecho cuando** (es el «Hecho cuando» de la Fase 7 del PLAN): otra persona descarga el editor desde la página de versiones, crea un personaje y lo usa en Godot **sin ayuda**. El responsable anota en el registro quién lo probó y dónde se atascó.

## 2. Nivel de modelo

**Simple** para preparar el paquete y las notas. Todo comando de `git` y de `gh` lo ejecuta el responsable (regla 8).

## 3. Contexto mínimo

- `ruta/pasos/7.1_builds_linux.md`, §5 y §6.
- `PLAN.md`: «Qué es el MVP» (líneas 11–22) y las reservas abiertas (`grep -n -i 'reserva' PLAN.md`).
- `README.md` ya reescrito (7.2).

## 4. Archivos

- **Se crean:** `pruebas/fase_7/empaquetar.sh`; `NOTAS_0.1.0.md` dentro de `build/` (no entra en git; su texto se pega en GitHub).
- **Se toca:** `PLAN.md` (marcar el paso y el registro), `README.md` (quitar cualquier «próximamente» que ya sea verdad).
- **No se toca:** código. Si al empaquetar aparece un fallo, se vuelve al paso que lo arregla; no se parchea aquí.

## 5. Diseño

1. **Lista previa** (cada punto con su comando y resultado):
   - Todas las pruebas sin ventana pasan (`GUIA_MODELOS.md` §5 tiene el bucle).
   - `probar_build_linux.sh` → `AUTOPRUEBA: TODO BIEN`.
   - `probar_readme.sh` y `probar_licencias.gd` pasan.
   - `git status --short` vacío (lo mira el responsable): nada sin guardar.
   - `config/version` de `project.godot` = `0.1.0`.
   - El revisor-visual pasó en el cierre de la Fase 6 y no quedan reservas sin decidir.
2. **Paquete** (`pruebas/fase_7/empaquetar.sh`):
   ```sh
   #!/bin/sh
   # 7.4: crea el .zip de la versión y su suma de control.
   # Uso: pruebas/fase_7/empaquetar.sh 0.1.0
   set -e
   v="$1"; [ -n "$v" ] || { echo "ERROR: falta la versión"; exit 1; }
   root=$(cd "$(dirname "$0")/../.." && pwd)
   out="$root/build/GameMolde-$v-linux"
   rm -rf "$out"; mkdir -p "$out"
   cp "$root/build/linux/gamemolde.x86_64" "$root/LICENSE" "$root/CREDITOS.md" "$out/"
   cp "$root/README.md" "$out/LEEME.md"
   chmod +x "$out/gamemolde.x86_64"
   (cd "$root/build" && zip -r -q "GameMolde-$v-linux.zip" "GameMolde-$v-linux" && sha256sum "GameMolde-$v-linux.zip" > "GameMolde-$v-linux.zip.sha256")
   echo "RESULTADO $(ls -l "$root/build/GameMolde-$v-linux.zip" | awk '{print $5}') bytes"
   ```
3. **Probar el paquete, no el build:** descomprimir el `.zip` en una carpeta vacía y lanzar `./gamemolde.x86_64 --headless -- --autoprueba`.
4. **Notas de la versión** (`build/NOTAS_0.1.0.md`), 4 apartados cortos:
   - Qué hace (la lista de «Qué es el MVP» del PLAN, en pasado).
   - Requisitos (Linux de 64 bits, Vulkan).
   - Problemas conocidos: las reservas abiertas, en lenguaje llano (por ejemplo: «sin el archivo `.tres`, el borde de la prenda se ve dentado»).
   - Suma de control `sha256` del `.zip`.
5. **Publicar (lo ejecuta el responsable).** Comandos propuestos, para copiar:
   ```sh
   git tag v0.1.0
   git push origin v0.1.0
   gh release create v0.1.0 build/GameMolde-0.1.0-linux.zip build/GameMolde-0.1.0-linux.zip.sha256 \
     --title "GameMolde 0.1.0" --notes-file build/NOTAS_0.1.0.md --prerelease
   ```
   Recomendación (D29): publicarla como **versión preliminar** (`--prerelease`) hasta que una persona ajena la haya probado; después se quita la marca. Motivo: una preliminar se puede retirar sin que parezca una versión rota.
6. **Prueba con una persona ajena.** Solo se le da el enlace. El responsable mira sin ayudar y apunta cada duda. Las dudas se convierten en cambios del README (7.2) o en entradas propuestas para `IDEAS.md`.
7. **Windows:** si la Fase 8 ya está cerrada, el `.zip` de Windows se añade a la misma versión (ficha 8.4, D15). Si no, la 0.1.0 sale solo para Linux y Windows llega en la 0.1.1.

## 6. Prueba

| Comprobación | Límite |
| --- | --- |
| El `.zip` descomprimido en una carpeta vacía pasa la autoprueba | `AUTOPRUEBA: TODO BIEN` |
| `sha256sum -c GameMolde-0.1.0-linux.zip.sha256` | `OK` |
| Contenido del `.zip` | Exactamente 4 archivos: ejecutable, `LICENSE`, `CREDITOS.md`, `LEEME.md` |
| Tamaño del `.zip` | Se anota. PROVISIONAL: ≤ 60 MB (GitHub admite hasta 2 GB por archivo) |
| Descarga desde GitHub: el `sha256` del archivo bajado coincide | Igual |

**Que la prueba detecta el fallo:** borrar `gamemolde.x86_64` de la carpeta antes de comprimir → el punto 3 falla. Cambiar un byte del `.zip` → `sha256sum -c` falla.

## 7. Trampas conocidas

- El `.zip` «Source code» que GitHub añade solo **no trae los archivos de Git LFS**: no sirve para compilar. Decirlo en las notas.
- `.gitignore` ya ignora `*.zip` y, tras el 7.1, `build/`: el paquete no entra en el repositorio por accidente.
- Una etiqueta de git publicada no se debe mover. Si hay un fallo tras publicar, se saca la 0.1.1; no se reescribe la 0.1.0.
- `gh` puede no tener sesión iniciada: lo resuelve el responsable (`gh auth status`).
- No pongas autoría ni `Co-Authored-By` en ningún mensaje (regla 8).

## 8. Juicio visual

No hace falta uno nuevo. La página de la versión debe llevar una de las capturas ya elegidas en el 7.2.

## 9. Si te atascas

- Si la lista previa tiene un punto en rojo: **no se publica**. Informa y espera.
- Si la persona ajena no consigue terminar: el MVP no está cerrado. No lo marques como hecho; apunta dónde se paró.
